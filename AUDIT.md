## 2b. Correctness pass

A later audit re-read the whole codebase and drove the running server directly.
Five classes of defect were found. All are fixed; each fix carries a regression
assertion.

### Day-only columns disagreed with themselves

`new Date("2026-08-15")` parses as **UTC midnight**, but every reader used
**local** fields — `toLocaleDateString`, `getDate()`, `setHours(12)` followed by
`toISOString()`. West of UTC the two disagreed by a day. One metric row could
show as the 15th in its edit dialog, as the 14th in the table beside it, and be
charted under the 14th; content generated by a plan landed a day early, and the
calendar put hand-scheduled pieces on the wrong cell. Nothing in the suite
caught it because the suite only ever ran in UTC.

`src/lib/date.ts` is now the single crossing point. A day has no timezone, so it
is pinned to UTC midnight on the way in and read with UTC fields on the way out;
`localDayKey` covers the other frame — "today", and the calendar grid's cells,
which are local wall-clock days. Comparing the two means comparing `YYYY-MM-DD`
keys, each read in its own frame.

Two things fell out of the same change. An impossible date (`2026-02-31`) used
to roll over into 3 March and save silently; it is now refused. And an
unreadable date parsed to `Invalid Date`, which is never less than anything, so
`endDate < startDate` passed it through — campaigns and experiments now reject
it before the comparison.

`scripts/e2e-dates.sh` covers this, and is written to be run twice: once
normally, once with the server under a negative-offset timezone.

### Server actions trusted their parameter types

A server action is a public HTTP endpoint; a TypeScript parameter type
guarantees nothing at runtime. Five actions passed a caller-supplied value
straight into Prisma or into an object index:

| Action | With a bad value |
| --- | --- |
| `runRouteAction` | `AGENT_REGISTRY[agent]` was `undefined`, and the read threw *outside* the loop's try block — HTTP 500 |
| `setCampaignStatusAction` | Prisma rejected the unknown enum member — HTTP 500 |
| `setContentStatusAction` | as above |
| `setExperimentStatusAction` | as above |
| `setRecommendationStatusAction` | as above |

Each now checks the value against its own key list and returns a message. A
sixth, `editSectionAction`, had the opposite failure: an unknown section key
matched nothing, so the write saved the strategy unchanged and still reported
success. It is checked too.

### The overview dashboard was frozen at phase 04

Every module but Audience reported **"Ships in a later phase."**, and four
sections rendered fixed placeholders — *"Campaigns ship later"*, *"Content ships
later"*, *"Analytics ships later"*, *"Growth ships later"* — while the sidebar
linked to all five working modules and their tables held the operator's real
records. The product's main landing page was telling people their own data did
not exist.

`src/lib/dashboard/queries.ts` now counts the six areas for real, and the
dashboard renders what it finds: upcoming content, active campaigns, recent
insights and open recommendations, each linking to its module. An empty area
still says it is empty and offers the route that fills it — the rule against
fabricated zeros is unchanged; what changed is that "empty" and "does not exist"
are no longer confused. Next actions follow the critical path (profile →
strategy → audience → work → results → growth) instead of stopping at the
profile.

### Configuration named a package that is not installed

`serverExternalPackages` listed `@prisma/adapter-pg`, which this project does
not depend on, while `@prisma/adapter-libsql` — the adapter `src/lib/db.ts`
actually loads — went unlisted. Corrected.

`.gitignore` matched `.env*`, which also ignored `.env.example`: the file the
README tells people to copy. A fresh clone had no template. Re-included, and the
SQLite database file is now ignored explicitly so a `git add .` cannot commit a
real business.

### One shared pending flag for a list of rows

Deleting one analytics row disabled and spun the delete button on every row.
Scoped to the row being deleted.

## 3. Known limitations

Honest list. None of these are hidden in the interface.

**By design, per the master document**

- No authentication, accounts, teams or workspaces. LUMEN is a local
  single-operator tool.
- No advertising integrations. Meta, Google, TikTok and the rest are not
  connected; campaigns are planning objects and analytics is entered by hand.
- No publishing. Content statuses are editorial; `PUBLISHED` records that the
  operator posted it elsewhere.
- SCOUT has no internet access. It reasons only about competitors the operator
  records, and refuses to analyse an empty set.

**Genuine gaps**

- **Conversations cannot be deleted** from the interface. The action existed but
  had no caller, so the audit removed it rather than leave an untested write
  path. Restoring it is a small, deliberate change.
- **No migration history.** `schema.prisma` is the source of truth and
  `npm run db:push` applies it, but no Prisma migration files have been
  generated, so there is no ordered upgrade path between schema versions yet.
- **Backup restore is all-or-nothing.** There is no per-project import, and no
  merge — a restore replaces everything.
- **Analytics currency is per row.** Mixing currencies in one range suppresses
  money totals with an explanation rather than converting; there are no exchange
  rates.
- **The timezone setting is stored but does not yet drive anything.** Day-only
  columns are pinned to UTC midnight and read back in UTC (see section 2b), so
  they are stable everywhere; what the setting would add is displaying an
  *instant* — an agent run's timestamp, say — in a zone other than the
  machine's.
- **The `/api/ai/selftest` route ships enabled** but is hard-gated to the mock
  provider, so it cannot reach a real vendor or spend anything.
- **The Gemini, Groq and OpenRouter happy paths are unverified against a live
  API.** All three were exercised end to end — request construction, network
  call, error conversion, sanitisation, and the settings display — but this
  environment's egress proxy blocks all three hosts, so only the failure path
  was observed returning real HTTP status codes. A successful completion has
  not been seen; confirming one needs a real key tested from an environment
  this proxy does not sit in front of (a local machine, or the deployed app).
- **No automated accessibility or visual regression testing.** Contrast was
  verified by computation during phase 19, not by a test that runs on every build.
- **Tests require a running server.** They are end-to-end HTTP suites, not unit
  tests, so `npm start` must be up before `scripts/e2e-*.sh`.

**Environment caveat carried since phase 1**

`prisma/sql/schema.sql` is a hand-written mirror of the schema, used only where
the Prisma CLI cannot download its engine. On a normal machine `schema.prisma`
is authoritative — use `npm run db:push`.

## 4. Running LUMEN locally

Requirements: **Node.js 20.9+**. Nothing else — the database is a file, and no
C++ compiler or build tools are needed on any platform.

```bash
npm install                 # runs prisma generate automatically
cp .env.example .env        # then edit it (see below)
npm run db:push             # creates prisma/lumen.db from the schema
npm run dev                 # http://localhost:3000
```

**Minimum `.env`**

```bash
DATABASE_URL="file:./prisma/lumen.db"
NEXT_PUBLIC_APP_URL="http://localhost:3000"
AI_PROVIDER="mock"
```

With `AI_PROVIDER="mock"` every screen works and every agent returns placeholder
text, so the product can be explored with no key and no cost.

**For real AI output**

Four options. Three are free and need no credit card.

```bash
# Google Gemini — widest free daily allowance (key: aistudio.google.com/apikey)
AI_PROVIDER="gemini"
GOOGLE_API_KEY="..."

# Groq — much faster, smaller daily allowance (key: console.groq.com/keys)
AI_PROVIDER="groq"
GROQ_API_KEY="gsk_..."

# OpenRouter — one key reaches hundreds of models (key: openrouter.ai/keys).
# AI_MODEL is not optional pinning here, it is the actual choice of model —
# the default is free with its own small daily/per-minute limit.
AI_PROVIDER="openrouter"
OPENROUTER_API_KEY="sk-or-v1-..."

# Anthropic — paid
AI_PROVIDER="anthropic"
ANTHROPIC_API_KEY="sk-ant-..."
```

`AI_MODEL` is optional for every provider except OpenRouter, where it is the
model choice itself; each provider (OpenRouter's default included) has a
sensible default if left unset.

**Privacy note:** on Google's free tier, prompts may be used to improve their
products. Groq's free tier and all paid tiers do not do this. OpenRouter's
policy depends on which backend model routes the request, so check the
specific model's page on openrouter.ai before sending sensitive business data
through a free one. If the business data is sensitive, prefer Groq or a paid
tier.

Restart after editing. Confirm it took effect at **Settings → AI → Test
connection**. Your key is never displayed, logged, or written to a backup.

**Production mode locally**

```bash
npm run build
npm start
```

**Running the tests**

```bash
npm start                      # in one terminal
bash scripts/e2e-projects.sh   # any suite, in another

# The date suite is timezone-sensitive by design. Run it under a zone that is
# not UTC as well, and it must pass identically:
TZ=America/New_York npm start
bash scripts/e2e-dates.sh
```

## 5. Backup and restore

**Export** — Settings → Backup → *Export a backup*. Downloads a JSON file
containing every project, profile, strategy, segment, competitor, insight,
content item, campaign, budget, metric, recommendation, experiment, conversation
and agent run, stamped with a format version.

The file contains **no API keys and no credentials**. Keys live in `.env`, never
in the database, so they cannot reach an export.

**Restore** — Settings → Backup → choose the file. LUMEN validates the format
version and shows what the archive holds *before* anything is touched. Confirm by
typing `REPLACE`.

A restore **replaces everything**. Export a backup of what you have first.

The restore runs in a single transaction: if it fails partway, it rolls back and
your existing data is untouched. This is tested — a suite feeds it an archive
with a broken foreign key and asserts nothing changed.

**Recommended habit:** the whole database is one file. Copying
`prisma/lumen.db` is also a complete backup, and is the fastest way to snapshot
before an experiment.

## 6. What must change for SaaS

The local architecture was built so this list stays short.

**Must change**

| Area | Local now | SaaS |
| --- | --- | --- |
| Database | SQLite file via libSQL | PostgreSQL — the five JSON-encoded list columns become `text[]`, and `mode: "insensitive"` filters replace the two application-level comparisons |
| Identity | None | User → Workspace → WorkspaceMember above Project |
| Authorisation | Project id is the scope | Project id becomes a scope identifier only; every query gains a membership check |
| AI usage | Logged per run | Metered per user, workspace and plan |
| Backup | Local file download | Cloud backup with retention |
| Settings | Singleton row | Per workspace, and per user for preferences |

**Reusable without redesign**

Every marketing module, all six agents, the provider abstraction, the agent
runtime with its retries and timeouts, `ProjectContextBuilder`, the design system
and component library, and the recommendation and experiment logic.

**Already SaaS-shaped**

- Every business record carries `projectId` and cascades from it.
- `AgentRun` already stores provider, model, tokens, latency and attempts, so
  metering needs `workspaceId` and `userId` columns — additive, not a rewrite.
- Server actions are the only write path; there is no client-writable API to
  re-secure.
- No secret is reachable from a client bundle: `getServerEnv()` throws in the
  browser, and the client schema contains only `NEXT_PUBLIC_*` keys.
- Money is always stored with its currency.
- Provenance (`AI` / `MANUAL` / `EDITED`) and confidence are modelled on the
  records themselves, so multi-user attribution is an added column rather than a
  new concept.

**The one architectural decision to revisit**

Active project lives in an httpOnly cookie. That is correct for a single
operator, but in SaaS the active project must be validated against workspace
membership on every request — the cookie becomes a hint, never an authorisation.

---

## 7. Verdict

The local MVP is **ready for daily use** by a single operator, with the
limitations above understood.

The one thing that has not been proven is AI output quality: every agent has been
exercised end to end against the mock provider, but no agent has been run against
a real model. Configure a key and use it on a real business before building
anything further — if the prompts need work, that is far cheaper to learn now
than after a SaaS migration.
